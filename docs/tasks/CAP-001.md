# CAP-001：建立有版本与证据等级的能力台账

- 状态：DONE
- 前置：TEST-001
- 证据目录：`work/upgrade/CAP-001/`

## 目标与产出

创建 `docs/compat/CAPABILITIES.md`、`docs/compat/capabilities.json` 及 schema/校验入口。
记录主线 API 36 / android-16.0.0_r2 来源和现有 SDK 声明策略；不改变生产实现或默认值。
JSON 是可维护的事实数据，不是替所有 API 生成成功返回的配置。

## 步骤

1. 查 GitHub 类似能力清单/签名检查实现；复用本仓库已有 DEX/class/ELF 解析入口。
2. 用构建 classfile、native 导出和注册位置建立自动库存；不要用 grep 方法声明替代签名解析。
3. 定义稳定 ID、subsystem、API/ABI 版本、签名/服务接口、实现位置、AOSP 来源、
   支持状态、限制、测试 ID、验证版本/日期、gap ID、相关 gate 等字段。
4. 支持状态使用 implemented / partial / unsupported / missing / unknown；
   验证状态独立使用 unverified / contract-tested / android-compared，并关联具体用例与环境。
   declared 存在不等于 implemented；缺少证据默认 unknown/unverified。
5. 第一批人工核实至少 20 项，覆盖资源、生命周期、Parcel/Binder、Surface/调度、媒体、native ABI 六类；
   包含 ServiceManager 各方法与 PresentedSdk 版本声明，优先连接已有测试。
6. public SDK、hidden API、JNI/动态注册、Bionic、service/property 分开；各说明来源/分母/扫描盲区。
   源码与测试或版本变化时条目标 stale 并等待重验，不能沿用旧绿色状态。

## 验收

- [x] schema 拒绝重复 ID、非法状态、悬空测试引用及缺依据的 verified 条目。
- [x] 重复生成库存可得到相同排序/内容；继承方法、重载/描述符及类/接口区别不误算。
- [x] 20 项满足字段并可追溯；给出局部覆盖分母与 unknown 数，不宣称全 Android 完整率。
- [x] 本卡不改生产行为，不将实验开关与支持能力合并成一个状态。
