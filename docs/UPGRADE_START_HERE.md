## 3. 你需要掌握的几个词

| 名称 | 可以这样理解 |
|---|---|
| 仓库 repository | 项目文件与版本历史 |
| 分支 branch | 某条改动路线，尚未合并前可以独立验收 |
| 工作区 worktree | 同一仓库的另一套可编辑文件，适合隔离实验 |
| 提交 commit | 能找回的版本检查点；不包含未跟踪、被忽略文件和应用数据 |
| 差异 diff | 本次到底改了哪些内容 |
| 回归测试 | 确认旧功能没有被新改动破坏 |
| CI | 提交后由自动环境执行的一组检查；本项目现有 CLA 流程不等于产品测试 |
| PR | 提交给远端仓库审阅/合并的改动提案 |
| 基线 baseline | 改动前的版本、测试结果和测量证据 |
| ADR | 对一项架构选择记录理由、替代方案和回退方法 |

## 4. 每个任务都重复这个流程

1. **开始**：让 Codex 读取任务卡，报告分支、基础提交、变更范围和验收方法。
2. **执行**：只实施该任务；新发现的问题登记，不顺手大改。
3. **验证**：要求列出 PASS、FAIL、SKIP、NOT_RUN 和证据。只说“应该可行”不算完成。
4. **检查改动**：看改了哪些文件；文档任务不应突然改变 runtime 源码。
5. **评审**：在 Git 项目内使用 `/review`。未提交选择未提交变更，已提交选择相对正确基础分支/提交的变更。
6. **修正**：对明确的缺陷要求修复并重跑受影响检查。
7. **保存**：通过后保存本地 commit，并更新任务卡与 `PROJECT_STATE.md`。
8. **下一项**：依赖满足后再开始；不要把“任务卡写好了”误当作任务完成。

评审提示词：

```text
只审查本次任务改动，不修改文件。
以任务卡验收条件为依据，检查错误行为、线程/生命周期、应用专用分支、
测试被削弱、无证据的性能结论、正式安装或共享 runtime 的意外改写。
区分确认缺陷与待验证猜测；指出具体文件和位置。
检查新增未跟踪文件，不能只读 git diff 的已跟踪部分。
```

评审 AI 没有发现问题不代表一定正确，仍要结合运行证据和实际使用结果。

## 6. 怎样使用旧研究报告

- 保留“通用兼容修复、小任务、先测量、可回归”的原则。
- 报告中的六个月是建议路线，不是工期承诺；先完成基础任务再排序。
- 本地 `origin` 是上游，`fork` 才是 Rengwang。同步前查清目标，不直接执行泛化的 `git pull` 或 `git push origin main`。
- 报告的文件引用标记不能代替可访问的源码/官方文档位置。
- SurfaceStackLab、EglSwapLab、Doctor、统一调度器等有些只是建议，不可拿不存在的测试作完成条件。
- readback 路径确实在构建文档中出现，但是否为你的主要瓶颈需要采样。
- `AGENTS.md` 保留简短的常用规则，详细信息放任务卡和专题文档，避免每次塞入整份长报告。

## 7. 出问题时怎么说

环境缺失：

```text
先停止当前构建，不修改业务代码。
告诉我缺的是哪项依赖、当前实际版本、最小解决办法和会修改哪些位置。
区分环境阻碍、既有代码缺陷和本轮新增问题。
```

改动失败：

```text
先保留日志和当前改动，不 reset --hard，不删除测试。
定位首个有效失败；只修复当前任务引入的问题。
如果需要回退，先区分源码、构建产物、共享 runtime 和应用数据，
给出保留证据的最小回退步骤。
```

Git 回退只改变源码历史；已经安装的二进制和应用数据不会因此自动恢复。
当前阶段不触及正式安装，所以主要通过独立分支保留/放弃实验。

## 8. 什么时候可以大规模重构

至少先有：可复现构建、适用测试入口、跨类型兼容样本、可重复性能结果、
目标模块的行为契约和可回退设计。
ARCH-001 对 Surface/调度/Canvas 等候选作证据比较；PILOT-001 只验证一个小切口。
只有证据支持时，才把统一调度器、GPU Canvas 等方向拆成新的任务。
